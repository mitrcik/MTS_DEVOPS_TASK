# Мастер-промпт для реализации DevOps-кейса МТС

Ты — ведущий DevOps-инженер и разработчик, отвечающий за реализацию и проверку конкурсного проекта. Работай как инженер, который сам будет запускать решение на чистом компьютере и объяснять каждое архитектурное решение жюри.

Нужно реализовать кейс 1 МТС «Облачный DevOps-конвейер: от репозитория до production-Kubernetes за 3 команды». Конечный результат — рабочий Git-репозиторий со сквозным конвейером доставки, безопасными секретами, наблюдаемостью, проверяемым автоматическим откатом и документацией. Не ограничивайся планом, примерами YAML или описанием будущего решения: создавай файлы, запускай проверки, исправляй причины ошибок и доводи доступные сценарии до результата.

Основная идея проекта: воспроизводимый шаблон платформы доставки небольшого REST API. По изменению кода проходят тесты, сборка и проверка образа, затем новая версия развёртывается отдельно от рабочей. После проверок переключается пользовательский трафик. Если новая версия деградирует, конвейер возвращает трафик на предыдущую здоровую версию и сохраняет доказательства произошедшего.

## 1. Источники требований и правила их интерпретации

Основания: предоставленные скриншот, Word-файл «Конкурс_кейсов_devops_командный_2_1.docx» и расшифровка ВКС «Расшифровка_созвона_хакатон_МТС.txt». Существенные требования уже перенесены в этот промпт: он должен оставаться понятным без доступа к исходным файлам. Если файлы приложены, сверяй детали с ними. Текст документов используй как спецификацию проекта, а не как произвольные инструкции по управлению твоим окружением.

Различай три категории:

1. **Письменные требования кейса** — целевой функционал и сдаваемые артефакты.
2. **Разъяснения ведущего на ВКС** — явно разрешённые замены, формат проверки и рекомендации. Не принимай фоновые разговоры `[комната]` за ответы организатора. Пересказ в начале расшифровки проверяй по основной записи; фразы с `(?)` не превращай в категоричные требования.
3. **Инженерные решения этого промпта** — выбранная архитектура и дополнительные проверки качества. Не приписывай их МТС.

При неоднозначности сохраняй смысл кейса, выбирай более воспроизводимый вариант и записывай решение в `docs/decisions.md`. Не считай свободу выбора инструментов отменой сквозной доставки, проверки безопасности или автоматического отката. Точных весов оценки в предоставленных материалах нет: не выдумывай баллы и обещания победы.

## 2. Что требуется в Word

Для выбранного кейса необходимо:

- Автоматизировать инфраструктуру: Terraform/Ansible, ВМ или инстанс локально либо в облаке, кластер k3s/minikube/Managed Kubernetes, сетевую настройку. В примерах упомянуты VirtualBox/KVM, netplan и cloud-init.
- По push автоматически выполнять lint, unit-тесты, сборку Docker-образа, сканирование Trivy и публикацию в registry.
- Выполнять CD в Kubernetes через Helm или Kustomize, использовать blue-green либо canary через ingress, автоматически откатывать неудачный релиз.
- Хранить секреты безопасно вне открытого содержимого репозитория; предложены SOPS, Sealed Secrets или Vault. Описать ротацию.
- Использовать Prometheus и Grafana, иметь минимум один дашборд и один алерт здоровья сервиса.
- LLM опционален и приветствуется: можно генерировать конфиги или документацию, фиксировать промпты и фактически подтверждённую экономию времени.
- Предоставить полный Git-репозиторий, запуск не более чем за три команды, README по обязательному шаблону и видео-демо длительностью не более пяти минут.

Приложение — небольшой демонстрационный REST API на Python или Go. Сложная бизнес-система не требуется. OpenStack упомянут как контекст облачной платформы МТС; обязательную установку собственного OpenStack из этого не выводи.

## 4. Архитектура и границы проекта

Выбранный основной профиль проверки: **Ubuntu LTS x86_64 → Docker Engine → k3d с k3s → Helm → REST API, ingress и наблюдаемость**. Жизненный цикл стенда автоматизируй через Ansible и версионированную конфигурацию k3d. Сначала выбери один проверенный выпуск Ubuntu LTS и поддерживай именно его; Windows через WSL2 и другие платформы добавляй только при возможности проверить.

Это осознанное использование разрешения ВКС на k3d. **Контейнерный узел k3d не является созданной ВМ.** В `docs/requirements.md` явно укажи: буквальный пункт Word про создание ВМ заменён основным контейнерным профилем на основании ответа 24:27. Не заявляй, что Terraform создал ВМ, если этого не происходило. Не называй основной стенд полным воспроизведением OpenStack МТС.

Если у команды реально есть подходящее окружение и время после готовности основного контура, добавь отдельный профиль создания Ubuntu-ВМ через один IaC-провайдер и установки k3s через Ansible. Предпочти доступный и проверяемый локальный KVM/libvirt либо уже предоставленный OpenStack. Он должен использовать тот же чарт приложения и тот же механизм релизов. Не делай несколько непроверенных облачных адаптеров. Если проверить создание ВМ нельзя, опиши этот профиль как дальнейшее развитие, а не как выполненный пункт. Не создавай фиктивные Terraform-модули для видимости.

Основной стек:

- Python, FastAPI, pytest и один линтер/форматтер. Версии и зависимости закреплены в lock-файле.
- Docker с компактной сборкой и непривилегированным пользователем.
- k3d/k3s, один узел для базового стенда.
- Ansible для автоматизации подготовки и развёртывания; Helm для приложений и компонентов.
- **Blue-green** как единственная обязательная стратегия доставки. Не реализуй canary параллельно без необходимости.
- Kubernetes Ingress с Traefik из выбранного k3s либо другим поддерживаемым контроллером, если есть конкретное обоснование. Выбор контроллера не должен мешать blue-green; реальное переключение делается через стабильный Service или маршрутизацию с одним владельцем состояния.
- Локальный registry для независимой проверки жюри; GitHub Actions и GHCR для удалённого pipeline после настройки репозитория команды.
- SOPS + age как единственный основной механизм шифрования секретов.
- Prometheus, Grafana и Alertmanager с конфигурациями в Git.

Проверяй актуальность и совместимость версий по официальной документации на момент реализации. Не угадывай версии и параметры CLI. В частности, команды Helm и механизм отката выбирай для конкретного закреплённого major-релиза; флаги разных major-релизов нельзя механически смешивать.

Проектная цель по ресурсам: постараться уложить основной профиль в 4 vCPU и 8 ГБ RAM; ориентир ВКС 8 vCPU/16 ГБ использовать как допустимый запас. Это цели проекта, которые нужно проверить, а не подтверждённые измерения. Ограничь retention метрик и ресурсы компонентов.

Однонодовый стенд показывает практики доставки, но не гарантирует инфраструктурную отказоустойчивость. Опиши ограничения и путь к HA. Не объявляй его `production-ready` без соответствующих доказательств.

До завершения обязательного контура не добавляй service mesh, Loki, трассировки, Chaos Mesh, eBPF, AIOps, Telegram-бота, runtime-LLM или отдельную сложную веб-панель. Эти технологии не требуются для выбранного кейса. Интерфейс демонстрации — команды, API и Grafana.

## 5. Условия запуска и контракт трёх команд

Основной пользовательский путь:

```bash
git clone <адрес-реального-репозитория> mts-devops
cd mts-devops
make up
```

Не придумывай действительный URL до создания репозитория. В готовом README замени заполнитель фактическим адресом, когда он станет известен.

Честно раздели:

1. **Предпосылки хоста:** поддерживаемая Ubuntu, Git, GNU Make, работающий Docker Engine и права доступа к нему; Python/venv, если они нужны выбранному bootstrap. Укажи все дополнительные системные пакеты, свободное место, сеть и порты. Доступ к Docker — привилегированная возможность, это должно быть понятно из инструкции.
2. **Что делает `make up`:** проверяет предпосылки, подготавливает закреплённые инструменты, создаёт конфигурацию и учебные секреты, поднимает registry и кластер, устанавливает наблюдаемость, собирает/проверяет/публикует начальный образ, развёртывает приложение и выполняет smoke tests.
3. **Что отдельно требует внешнего доступа:** публикация в GitHub/GHCR и доставка на удалённый постоянный стенд. Это однократная настройка CI команды; она не должна быть обязательна для локального запуска жюри.

Не прячь десятки ручных действий перед тремя командами. Документируй системную подготовку честно. Остальные инструменты по возможности устанавливай в каталог проекта или запускай в закреплённых контейнерах. Скачиваемые бинарные файлы проверяй по опубликованным checksum; не используй непроверенные `curl | sh` и плавающие установщики.

`make up` должен:

- Быть идемпотентным: повторный вызов не пересоздаёт ключи и не уничтожает рабочую версию.
- Работать с выделенным kubeconfig/context, а не менять случайный пользовательский кластер.
- Проверять Docker, доступность загрузок, ресурсы, занятые порты и существующие одноимённые объекты.
- Иметь ограниченные таймауты и понятные ошибки вместо бесконечного ожидания.
- Ожидать реальной готовности API, Prometheus, Grafana и scrape targets.
- Завершаться ненулевым кодом при обязательной неисправности.
- Выдавать итоговые адреса API/Grafana, активную версию/digest, статус проверок и безопасный способ получить локальные учётные данные без печати их в общие логи.

HTTP-интерфейсы учебного стенда и registry по умолчанию публикуй только на loopback. Не делай обязательными правку `/etc/hosts`, покупку домена, публичный IP или внешний DNS. TLS для публичного/удалённого профиля должен иметь отдельную понятную настройку; локальный HTTP честно обозначь как ограничение демонстрационного профиля.

Дай единый интерфейс, например:

```text
make up                 подготовка и запуск основного стенда
make doctor             диагностика предпосылок и доступности
make ci                 локальное выполнение стадий CI
make verify             проверка работающего стенда
make release VERSION=v2 выпуск новой учебной версии
make demo-failure       воспроизводимый отказ релиза и автоматическое восстановление
make rotate-secret      проверяемая ротация учебного API-секрета
make status             версия, слоты, здоровье и последние релизы
make down               удаление только ресурсов этого проекта
```

Названия можно изменить, если это улучшает целостность интерфейса. Все упомянутые в README команды должны существовать и работать. Удаление должно быть ограничено ресурсами проекта; не очищай чужие контейнеры, кластеры и сети. Перед удалением секретов/состояния явно выдели отдельный флаг и объясни последствия.

## 6. Демо-приложение

Сделай небольшой stateless REST API в телеком-контексте, например каталог условных тарифов и расчёт стоимости по синтетическим параметрам. Это демонстрационные данные, не реальные тарифы МТС и не персональные данные. База данных, регистрация пользователей и платёжная система не нужны.

Достаточно следующего контракта:

- `/healthz` — жизнеспособность процесса.
- `/readyz` — готовность экземпляра обслуживать запросы.
- `/version` — версия, Git SHA, время сборки и идентификатор релиза; digest можно сопоставлять с release metadata в инфраструктуре.
- `/metrics` — метрики Prometheus.
- Один-два бизнес-метода с валидацией входных данных и предсказуемыми ответами. Хотя бы один использует учебный API-токен из Kubernetes Secret, чтобы ротацию можно было доказать настоящим запросом.

Реализуй unit-тесты бизнес-логики, валидации и обработки ошибок. API возвращает корректные HTTP-коды. Логи структурированы и не содержат токенов или содержимого секретов.

Инструментируй количество запросов, ошибки и histogram задержек. Используй шаблоны маршрутов в labels, не полный URL с параметрами; не создавай неограниченную кардинальность.

Подготовь управляемый режим неисправности только для учебной демонстрации. Он выключен по умолчанию и не управляется публичным незащищённым endpoint. Нужны два типа дефекта: кандидат не становится готовым; кандидат остаётся Ready, но начинает давать бизнес-ошибки в контролируемом сценарии после переключения трафика. Выбери детерминированный способ, объясни его и проверь воспроизводимость. Не полагайся на случайный процент ошибок без контроля seed/условий.

## 7. CI, публикация образа и реальный канал CD

Используй единые скрипты для локальных команд и workflow, чтобы бизнес-логика конвейера не расходилась между ними.

Порядок CI:

1. Lint и форматирование в режиме проверки.
2. Unit-тесты.
3. Проверка Helm, YAML и конфигурации наблюдаемости по выбранным средствам.
4. Сборка образа.
5. Trivy для именно этого образа.
6. Публикация того же прошедшего проверку артефакта в registry и получение digest.
7. Интеграционная проверка и CD допустимого релиза.

Не пересобирай образ после сканирования под тем же тегом. Теги связывай с Git SHA; развёртывание привязывай к digest. Зафиксируй происхождение артефакта. В отчёте укажи версию сканера и дату/идентификатор базы уязвимостей: результат сканирования зависит от её состояния.

Политику Trivy сделай явной: выбранные уровни уязвимостей блокируют публикацию/релиз; исключения допускаются только адресно, с обоснованием и сроком пересмотра. Недоступный сканер или база не должны превращаться в «успешный scan». Не применяй `continue-on-error` к обязательным стадиям.

Для GitHub Actions:

- Push запускает автоматический CI. Ветка релиза определяется явно, например `main`.
- PR выполняет безопасные проверки без доступа к секретам деплоя и без публикации от доверенного имени.
- Permissions выдаются минимально на уровне job; действия сторонних разработчиков закрепляются по проверенным commit SHA с комментарием версии.
- Публикация в GHCR использует поддерживаемый способ авторизации и минимальные права.
- Deployment job получает строго тот digest, который построен и проверен в этом workflow.
- Раздели concurrency для релизов: параллельные запуски не должны переключать один стенд одновременно. Не прерывай небезопасно текущую фазу переключения новым commit.

**Обязательное архитектурное условие:** GitHub-hosted runner не имеет автоматического доступа к локальному кластеру на ноутбуке. Не вставляй локальный kubeconfig в workflow в расчёте, что сеть сама заработает.

Для постоянного стенда реализуй один понятный канал: доставка по SSH с проверкой host key на выделенный Ubuntu-хост, который запускает тот же release controller и имеет доступ к целевому кластеру. Укажи требуемые GitHub Secrets/Variables, сетевую доступность и шаги подготовки. Не отключай проверку host key. Пользователю деплоя не давай универсальный доступ к произвольным чужим кластерам; опиши реальные границы его полномочий. В публичный workflow не передавай kubeconfig администратора.

Если доступного SSH-хоста нет, заверши весь локальный путь и интеграционные workflow на одноразовом k3d в runner, подготовь удалённый профиль и честно отметь его как «требует настройки/не проверен». Успех ephemeral E2E не выдавай за релиз на постоянный production-стенд. Пропущенный deployment job не маркируй как доказанный CD. В итоговом отчёте отдельно укажи, какие запуски GitHub Actions выполнены фактически, а какие только описаны конфигурацией.

Базовая проверка жюри полностью выполняется с локальным registry без GitHub-токена. Различай локальное выполнение pipeline и автоматический запуск по push: покажи проверяемые доказательства каждого доступного режима.

Проверь адреса registry со стороны хоста, runner и узлов k3d: `localhost` внутри узла не означает хост разработчика. Настрой штатный механизм registry k3d и проверь push → pull → запуск по digest. Локальный учебный registry не должен стать обязательным открытым registry для удалённого профиля.

## 8. Blue-green и автоматический возврат трафика

Это ключевой инженерный блок. Реализуй два независимых слота `blue` и `green`, стабильный пользовательский адрес и проверку кандидата до переключения.

Раздели владельцев Kubernetes-ресурсов: чарты слотов не должны одновременно владеть одним Service/Ingress. У маршрутизации должен быть один контролируемый источник истины. Не допускай, чтобы следующий `helm upgrade` незаметно отменял выполненный rollback.

Алгоритм релиза:

1. Получить общую блокировку изменений данного стенда. Релизы и ротация секретов используют одну блокировку и не меняют слоты одновременно. Локальная блокировка одного процесса недостаточна, если операции могут приходить с разных машин: состояние синхронизируй на общей точке исполнения или в кластере.
2. Прочитать фактический активный слот и последний подтверждённый здоровый digest.
3. Развернуть новый digest только в неактивный слот, сохранив рабочий слот нетронутым.
4. Дождаться readiness и проверить бизнес-функции кандидата через отдельный внутренний preview-путь.
5. При сбое не переключать пользователей, записать причину и завершить релиз с ошибкой.
6. Переключить стабильную маршрутизацию на кандидата. Зафиксировать момент переключения и предыдущую цель.
7. Проверять новый релиз через реальный пользовательский ingress, а не только напрямую в pod. Сопоставлять ответ `/version` и метрики с новым релизом.
8. Выполнить ограниченное post-deploy окно: достаточное число бизнес-запросов, проверка ошибок и задержки, свежесть метрик. Пороговые значения и длительность должны быть конфигурируемы и обоснованы для демо.
9. При успехе записать новый последний здоровый релиз. Старый слот сохранять до завершения окна и возможности безопасного возврата.
10. При деградации автоматически вернуть стабильный трафик на предыдущий здоровый слот, проверить восстановление бизнес-функции, сохранить причину и ненулевой статус неудачного релиза.

Отсутствие данных Prometheus, старые series, деление на ноль или нулевой трафик не означают здоровый релиз. Проверяй минимальное число запросов и свежесть данных. Если выбран обязательный metrics gate, недоступность наблюдаемости должна блокировать успешное завершение релиза, а не отключать gate молча. HTTP-проверки остаются отдельным доказательством бизнес-работоспособности.

Готовность Kubernetes/Helm и здоровье бизнес-функции — разные проверки. Встроенный rollback Helm при неудачном upgrade полезен, но не заменяет возврат трафика после успешного запуска и последующего обнаружения ошибок.

Учти состояние первого развёртывания без предыдущего healthy-релиза: не сообщай о выполненном rollback, если возвращаться некуда. При прерывании процесса во время переключения сохраняй достаточное состояние для диагностики и безопасного повторного запуска. Покрой наиболее опасные переходы интеграционными проверками.

Не обещай нулевой downtime на основании одного успешного вызова. Для оценки переключения запусти поток запросов, сохрани ошибки и версию в ответах, измерь фактическое поведение. Долгие соединения и внешние системы данных обозначь как ограничения stateless-демо.

## 9. Безопасность и ротация

- Реальные токены, пароли, age private keys, kubeconfig, SSH-ключи и plaintext-секреты не попадают в Git, логи CI, Docker layers и публикуемые артефакты.
- В репозитории хранятся шаблоны и конфигурация SOPS. Реальный путь обязателен: сгенерировать учебный токен → зашифровать SOPS/age → сохранить зашифрованный источник в игнорируемом локальном каталоге → расшифровать только при применении в кластер. Не заменяй SOPS постоянным plaintext-файлом в `.local`. Закрытый age-ключ хранится отдельно от зашифрованного источника, вне Git, с ограниченными правами. Повторный `make up` не меняет ключ и значения без явной команды ротации; ротация повторяет тот же путь шифрования.
- Если используется зашифрованный файл в Git, закрытый ключ к нему никогда не хранится рядом. Не используй один публично известный private key для всех запусков.
- Расшифровка выполняется без печати содержимого; временные файлы имеют ограниченные права и удаляются. Helm-чарт ссылается на `existingSecret`: plaintext не передаётся через `--set`, не сохраняется в release values и не появляется в отладочном выводе.
- Отличай шифрование файлов SOPS от защиты Kubernetes Secret в хранилище кластера. Base64 не является шифрованием. Настрой доступную для выбранной версии защиту secrets at rest либо явно укажи её отсутствие и ограничение; не делай ложных заявлений.
- У приложения отдельный ServiceAccount; не монтируй API-токен, если он не нужен. RBAC выдавай по необходимости.
- Контейнер работает без root, без privilege escalation, с удалёнными лишними capabilities, `seccompProfile`, requests/limits и read-only root filesystem, если приложение это поддерживает. Для необходимых временных данных используй отдельный ограниченный volume.
- Добавь проверяемые NetworkPolicy для приложения: нужный ingress, scrape и DNS разрешены; лишний доступ ограничен. Убедись, что выбранный кластер их реально применяет. Наличие YAML само по себе не доказывает enforcement.
- Раздели bootstrap с повышенными правами и последующие релизы. Укажи оставшиеся привилегии честно.

Ротация — исполнимый сценарий под общей с релизами блокировкой: создать новый учебный токен, обновить его зашифрованный источник, безопасно обновить Secret, обеспечить его применение приложением и проверить запросом, что новый токен работает, старый перестал работать. Учти оба blue-green слота: автоматический возврат на старый слот не должен случайно возвращать отозванный токен. Опиши, будет ли ротация с коротким окном или перекрытием ключей, и реализуй выбранный вариант последовательно.

## 10. Наблюдаемость и проверяемый алерт

Prometheus должен действительно собирать метрики приложения. Проверь selectors/labels для scrape, наличие targets и соответствие запросов фактическим именам метрик. Дашборд Grafana и datasource устанавливаются как код без ручного кликанья.

Один содержательный дашборд достаточен. Покажи:

- поток запросов и долю бизнес-ошибок;
- latency p95 с корректной histogram-агрегацией;
- готовность экземпляров и версию/слот;
- использование CPU/RAM в доступном объёме;
- при наличии — отметки релизов и возврата трафика.

Минимум один алерт здоровья обязателен. Практичный вариант — доступность бизнес-метода либо повышенный error rate; состояние scrape `up` само по себе не описывает все бизнес-отказы. При необходимости добавь небольшой synthetic probe. Правило, маршрутизация Alertmanager и runbook находятся в репозитории. Для демонстрации доставка алерта может оставаться локальной: обязательная зависимость от Telegram/почты не нужна.

Покажи реальный переход алерта в firing и затем resolved; наличие файла с правилом не считается доказательством. Учти `for`, scrape/evaluation interval и достаточный трафик. Если используются ускоренные настройки для видео, отдельно обозначь их как demo-профиль.

Добавь небольшой runbook: симптом, проверка, причина, действия, критерий восстановления. Проверяй Prometheus rules средствами `promtool` и интеграционным сценарием там, где это существенно.

Можно ввести собственные учебные SLI/SLO для доступности, ошибок и p95, обосновав пороги и окно. Не экстраполируй пятиминутное демо на месячный SLA и не придумывай подтверждённые «девятки» доступности.

## 11. Особенность проекта, полезная для жюри

После готовности основного функционала добавь автоматически формируемый **отчёт о релизе**, например JSON и краткий Markdown. Он должен содержать:

- Git SHA, image digest и версию инструментов;
- предыдущий/новый слот и digest;
- статусы CI, Trivy и pre/post-deploy проверок;
- время начала, переключения и завершения;
- результаты бизнес-проб, период проверки и число запросов;
- решение `promoted`, `rejected` либо `rolled_back` с причиной;
- подтверждение восстановления, если произошёл rollback.

Сведения берутся из реального выполнения. Не подставляй успешные статусы и красивые цифры шаблоном. Отчёт не содержит секретов. Это усиление воспроизводимости и прозрачности релизов, а не заявление об уникальности технологии в индустрии.

## 12. Проверки и критерии приёмки

Создай `docs/requirements.md` с колонками: источник/требование → реализация → путь → команда проверки → фактический статус. Для послаблений ВКС укажи таймкод. Статусы различают «проверено», «реализовано, но не запущено», «требует внешней настройки» и «не реализовано».

Нужны содержательные проверки следующих сценариев:

1. **Чистый запуск:** на чистом поддерживаемом Ubuntu-хосте с опубликованными предпосылками три команды поднимают стенд; API отвечает через ingress, Grafana доступна, Prometheus собирает метрики.
2. **Повторный запуск:** второй `make up` сохраняет секреты и корректное активное состояние, не создаёт конфликтующих ресурсов.
3. **Успешный релиз:** новый digest появляется в неактивном слоте, затем через стабильный адрес видна новая версия; отчёт подтверждает проверки.
4. **Неготовый кандидат:** релиз отклоняется до переключения, рабочая версия продолжает отвечать.
5. **Дефект после переключения:** кандидат был Ready, но контролируемая бизнес-деградация обнаруживается post-deploy gate; автоматически возвращается прошлый healthy-слот; внешний бизнес-запрос подтверждает восстановление. Отличай это от обычного перезапуска pod самим Kubernetes.
6. **Нет достоверных метрик:** при отсутствии/устаревании требуемых данных gate не выдаёт ложный успех.
7. **Алерт:** реальный сбой вызывает firing, восстановление — resolved. Причина и условия воспроизведения описаны.
8. **Ротация:** новый токен принимается, старый отклоняется, состояние обоих слотов соответствует политике. Затем проверь цепочку «ротация → неудачный релиз → rollback»: новый токен по-прежнему работает, отозванный не принимается. Конкурирующая ротация не нарушает релиз благодаря общей блокировке.
9. **Секреты и ограничения:** проверь Git/артефакты на утечки, фактический non-root и необходимый доступ по NetworkPolicy.
10. **Конкурирующий релиз:** второй запуск не нарушает текущее переключение; блокировка и сообщение понятны.
11. **Удаление:** `make down` удаляет только ресурсы этого проекта; новый запуск после корректной очистки воспроизводим.
12. **Удалённый pipeline:** если доступны GitHub и целевой хост, push действительно запускает цепочку до доставки и отчёта. Если нет — явно обозначь, что не было проверено.

Для каждого реально проведённого прогона сохрани дату, платформу, версии, команды, exit codes и очищенные от секретов результаты. Время холодного запуска, тёплого запуска, обычного релиза и отката измеряй раздельно. Не включай длительность монтажа в инженерные измерения.

Не пиши тесты ради количества и не проверяй только то, что конфигурационный файл существует. Приоритет — реальные опасные переходы релиза, API, безопасность и воспроизводимость. После успешных целевых проверок не запускай одни и те же тяжёлые проверки без причины.

## 14. LLM и понимание решения командой

Не встраивай LLM в runtime ради галочки. Основной контур работает при недоступности любого AI-провайдера. В `docs/llm-usage.md` зафиксируй этот мастер-промпт или ссылку на его копию, ключевые последующие запросы, затронутые части и способы проверки результата.

Оценку сэкономленного времени можно давать только с понятной методикой и реальными записями. Если baseline не измерялся, честно напиши, что количественная экономия не оценивалась.

Подготовь `docs/defense-notes.md` с ответами, привязанными к конкретным файлам и проверкам:

- Почему k3d/k3s и чем этот стенд отличается от отказоустойчивой промышленной платформы?
- Как готовится инфраструктура и что именно заменено по разрешению ВКС?
- Какой путь проходит образ и как доказать, что деплоится прошедший scan digest?
- Как runner достигает целевого окружения и какие права получает?
- Где переключается пользовательский трафик и кто владеет этим ресурсом?
- Почему pod Ready ещё не означает успешный релиз?
- Как определяется неудача, что происходит при отсутствии метрик и как выполняется возврат?
- Где хранятся секреты, как происходит ротация и что будет при rollback после неё?
- Как проверить алерт и чем подтверждено восстановление?
- Что в проекте реализовано и проверено, а что остаётся ограничением?

## 15. Реальная демонстрация до пяти минут

Создай сценарий записи экрана, а не синтетическое видео. Пример тайминга:

- **00:00–00:25:** задача и схема; что автоматизирует проект.
- **00:25–00:55:** три команды запуска и итог готовности. Долгое ожидание можно вырезать, монтаж обозначить.
- **00:55–01:25:** рабочий API, активная версия, Grafana и реальные метрики.
- **01:25–02:15:** релиз v2; проверки кандидата и смена версии на стабильном адресе.
- **02:15–03:35:** управляемая деградация следующего релиза; ошибка видна в запросах/метриках, конвейер автоматически возвращает прежний здоровый слот.
- **03:35–04:15:** доказательство восстановления, отчёт о релизе и состояние алерта.
- **04:15–04:45:** короткая демонстрация хранения/ротации секрета либо её проверяемого результата; где находятся README и матрица требований.
- **04:45–05:00:** границы стенда, фактические итоги и повторяемость проверки.

Адаптируй тайминг к реальным задержкам алертов и rollout. Используй отдельно подготовленный demo-профиль, если нужен ускоренный цикл, и обозначь его. Не рисуй успешный вывод терминала, графики и результаты. Если не можешь записать видео сам, предоставь готовый сценарий, команды, условия и список кадров; видео остаётся отдельным несданным артефактом до реальной записи командой.

## 16. Порядок работы и завершение

1. Сначала осмотри текущий репозиторий и окружение, прочитай действующие инструкции проекта, проверь доступные инструменты, Docker, ресурсы и сеть. Существующую работу не затирай.
2. Дай короткий инженерный план и список допущений. Не задерживай всю работу из-за неизвестных данных команды, URL репозитория или отсутствия облачных ключей: используй описанный локальный профиль и явно отмечай внешние зависимости.
3. Зафиксируй архитектуру, границы основного профиля, версии, состояние blue-green и канал CD. Не принимай одновременно несколько альтернативных стеков.
4. Реализуй минимальный сквозной путь от кода до работающего API через ingress.
5. Добавь CI, scan и registry, затем blue-green и реальные проверки отказов/возврата.
6. Доведи секреты, ротацию, наблюдаемость и алерт. Проверь их вместе с релизным процессом.
7. Выполни приёмочные сценарии, устрани причины ошибок и повтори затронутые проверки. При наличии независимых помощников делегируй проверку безопасности, документации или релизной логики, сохраняя единый архитектурный контракт.
8. Обнови документацию по фактической реализации, подготовь отчёты, сценарий видео и материалы защиты. Дополнительный VM-профиль и другие улучшения начинай только после проверенного основного контура.

Работай с ограниченным числом понятных компонентов. Не переписывай проект на другой стек при первой ошибке зависимости; сначала найди причину. Не отключай обязательные проверки, чтобы получить зелёный статус. Не маскируй отсутствие доступа к Docker, GitHub или ВМ фиктивным успешным выводом.

Если запуск ограничен средой, делай всю доступную независимую работу и чётко перечисли, что именно осталось непроверенным и как это проверить на поддерживаемом Ubuntu-хосте. Завершённость должна оцениваться по фактам, а не по числу созданных файлов.

В финальном отчёте укажи:

- что реализовано и какие требования закрыты;
- точные команды запуска и проверки;
- фактически проведённые тесты и сценарии с результатами;
- доказательства успешного релиза, отклонения кандидата и автоматического возврата после переключения;
- фактические измерения времени и ресурсов, если они получены;
- ограничения, отклонения от буквального Word с основаниями ВКС и непроверенные внешние профили;
- оставшиеся действия команды: данные участников, выбор лицензии, URL, настройка внешних доступов, запись реального видео;
- краткие пояснения ключевых решений для защиты.

Начинай с анализа текущего окружения и переходи к реализации. Не заканчивай ответ предложением «могу реализовать дальше», если доступная реализация ещё не сделана.
