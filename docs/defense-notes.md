# Материалы к защите

Короткие ответы на вероятные вопросы жюри со ссылками на файлы и проверки.
На консультации организаторы предупредили, что на защите спрашивают детали — например, «почему так
стартует контейнер и почему у него такие опции». Каждый пункт ниже команда должна уметь объяснить без
подсказки.

## Основные вопросы

### 1. Почему k3d/k3s и чем стенд отличается от отказоустойчивой промышленной платформы?

- k3d запускает настоящий k3s как контейнер Docker. Внутри работают API-сервер, kubelet, containerd,
  Traefik, контроллер NetworkPolicy kube-router и local-path. Стенд поднимается за ~15 с без
  гипервизора.
- Жюри проверяет проект на Ubuntu. Однонодовый k3d организаторы на консультации прямо разрешили.
  Решение D1 в `docs/decisions.md`.
- Отличия от production: один узел (нет HA control plane и рабочих узлов), хранилище kine/sqlite
  вместо etcd, HTTP на loopback без TLS, Prometheus без HA. Путь к HA описан в `docs/architecture.md`,
  раздел 7.
- Главное: свойства доставки не зависят от числа узлов. Это неизменяемый артефакт, проверка до и после
  переключения, откат, секреты и наблюдаемость. На стенде они проверяются по-настоящему.

### 2. Как готовится инфраструктура и что заменено по согласованию с организаторами?

- Цепочка запуска: `make up` → `scripts/playbook.sh` → `infra/ansible/up.yml`. Playbook выполняет
  роли по порядку: preflight (doctor), tools (sha256), secrets (age+SOPS), cluster (шаблон k3d),
  platform (PSA, NetworkPolicy, RBAC), observability, app (CI и первый релиз), summary.
- В кейсе есть пункт «Terraform/Ansible — ВМ/инстанс, netplan, cloud-init». По согласованию с
  организаторами он заменён контейнерным узлом k3d. **ВМ в проекте не создаётся, Terraform не
  используется** (D13).
- На готовой ВМ с Ubuntu 22.04/24.04/26.04 (x86_64 или arm64) всё ставят две команды: `make prereqs`
  и `make up` (D16, `docs/vm-guide.md`). Это проверено на чистых ВМ GitHub и в окружениях Ubuntu в
  контейнере.

### 3. Какой путь проходит образ и как доказать, что развёрнут именно тот digest, который прошёл сканирование?

Digest — неизменяемый идентификатор образа (`sha256:…`). Тег можно переназначить, digest — нельзя.

Конвейер `scripts/ci.sh`:

lint → test → validate → build (тег `<git-sha12>-<версия>`, запоминается image ID) → Trivy по этому
образу → **проверка, что тег всё ещё указывает на тот же image ID** → push → digest из `RepoDigests`
и сверка с ответом registry (`Docker-Content-Digest`) → `provenance.json`.

Release controller (`Artifact.from_provenance`) отказывает в релизе в двух случаях:
`trivy.result != passed` или digest в provenance не совпадает со ссылкой на образ. Чарт принимает
только ссылку вида `repo@sha256:…` (`values.schema.json`). В отчёте релиза указаны digest, версия
Trivy и дата базы уязвимостей.

Где проверить: `.local/artifacts/<tag>/provenance.json` и `.local/reports/release-*.md`.

### 4. Как runner достигает целевого окружения и какие права получает?

- GitHub-hosted runner **не** имеет доступа к кластеру на ноутбуке. Локальный запуск у жюри не
  зависит от GitHub.
- В GitHub работают jobs `checks` и `image` (сборка, Trivy, публикация в GHCR) и `e2e`. Job `e2e`
  поднимает одноразовый k3d внутри runner. Это интеграционная проверка, а не доставка.
- Доставка на постоянный стенд. Job `deploy` запускается только для ветки по умолчанию. Он передаёт
  `provenance.json` по SSH с проверкой `known_hosts` пользователю `deploy`. Для этого пользователя
  задана forced command `scripts/remote/deploy-gate.sh`: по SSH можно выполнить только её, а она
  принимает только `status` и `release`.
- На стенде релиз выполняет тот же `bgctl`. Он работает с kubeconfig ServiceAccount
  `release-controller`, у которого Role только в `mts-app`. Kubeconfig администратора не покидает
  стенд.
- **Статус: настроено, не проверено** — нет хоста (`docs/remote-cd.md`).

### 5. Где переключается пользовательский трафик и кто владеет этим ресурсом?

Релиз устроен по схеме blue-green: два слота приложения, трафик переключается между ними.

- Трафик переключается в Service `mts-api-active` (селектор `slot=blue|green`). Этот Service и Ingress
  принадлежат **только** Helm-релизу `mts-api-traffic` (`charts/traffic`).
- Слоты `mts-api-blue` и `mts-api-green` владеют своими Deployment, Service и NetworkPolicy.
  Маршрутизацию они не трогают.
- Переключение и откат выполняет только release controller (`_switch`).
- Схема чарта traffic требует явно указать `activeSlot`. Поэтому повторный `helm upgrade` не может
  незаметно вернуть «слот по умолчанию».
- Фактический активный слот читается из живого Service.

### 6. Почему pod Ready ещё не означает успешный релиз?

Readiness (`/readyz`) говорит только одно: процесс готов принимать запросы. Это значит, что хеши
токенов смонтированы и режим `not-ready` не включён.

Учебный дефект `errors-behind-ingress` показывает разницу. Кандидат (новая версия в неактивном слоте)
Ready и напрямую проходит все 16 preview-проверок. Но через ingress метод расчёта возвращает 500.

Поэтому после переключения есть окно проверки: реальный трафик через Traefik и проверка метрик.

### 7. Как определяется неудача, что при отсутствии метрик и как выполняется возврат?

**До переключения:**

- `helm --wait`: pod должны стать Ready, иначе Helm сам откатывает слот.
- Preview каждого pod: известный ответ расчёта, 401 без токена, 422 на неверный ввод, версия и
  release id, метрики.
- Prometheus обязан скрейпить кандидата.

**После переключения:**

- ~8 rps бизнес-запросов через ingress. Проверка останавливается досрочно, если доля неуспешных
  запросов > 2% на ≥ 20 запросах.
- Затем PromQL по слоту кандидата: число запросов, доля 5xx, p95 по histogram, свежесть scrape каждого
  pod, `app_build_info` с release id.

**Нет данных ≠ успех** (`scripts/pylib/gate.py`, 17 unit-тестов). Провалом считаются: недоступный
Prometheus, пустой вектор, NaN, мало трафика, устаревшая серия. В сценарии `no-metrics` релиз
отклоняется.

**Возврат:** `helm upgrade mts-api-traffic activeSlot=<прежний>` → ingress стабильно отдаёт прежний
release id → 10 с проверки без ошибок → `rolled_back` (код 3). При первом развёртывании возвращаться
некуда, поэтому результат — `failed`, а не `rolled_back`.

### 8. Где хранятся секреты, как ротация и что будет при откате после неё?

Подробно — в `docs/security.md`.

- Источник секретов — `.local/secrets/app-secrets.sops.yaml`, зашифрованный SOPS+age. Ключ хранится
  вне проекта: `~/.config/mts-devops/<cluster>/age.key`.
- В кластере лежит Secret с SHA-256 токенов. Он зашифрован в базе k3s.
- Ротация — `make rotate-secret`: перекрытие (действуют старый и новый токены) → проверка каждого pod
  обоих слотов → отзыв старого токена → проверка каждого pod и через ingress.
- Оба слота читают один Secret как файл. Поэтому откат на другой слот не вернёт отозванный токен
  (сценарий `rotation-chain`).

### 9. Как проверить алерт и чем подтверждено восстановление?

Команда `make demo-alert` проходит такой сценарий:

1. Активный слот масштабируется в 0. Это реальный сбой пользовательского пути.
2. Алерт `MtsApiSyntheticProbeFailing` переходит в pending, затем в firing — через ≈ 38 с после сбоя
   (scrape 5 с + `for` 30 с).
3. Алерт доходит до Alertmanager (маршрут `team-oncall-critical`).
4. Реплики восстанавливаются, и через ≈ 10 с алерт переходит в resolved.

Таймлайн сохраняется в `.local/reports/alert-demo-*.json`. Правила алертов дополнительно покрыты
`promtool test rules`.

### 10. Что реализовано и проверено, а что остаётся ограничением?

Статусы требований — в матрице `docs/requirements.md`, результаты проверок — в `docs/validation/`.

Ограничения:

- один узел;
- локальный HTTP;
- CD на постоянный стенд не проверен (нет хоста);
- ВМ не создаётся автоматически (Terraform/cloud-init); готовую ВМ с Ubuntu подготавливает
  `make prereqs` (`docs/vm-guide.md`);
- видео не записано.

## Частые уточняющие вопросы

| Вопрос | Ответ |
|---|---|
| Почему свой контроллер, а не Argo Rollouts/Flagger? | Меньше компонентов и CRD. Контроллер — ≈ 1 300 строк Python (`release.py` ≈ 760) без сторонних зависимостей. Этот код можно объяснить построчно. Те же шаги работают локально и на удалённом стенде. Для production разумно взять Argo Rollouts: модель та же (два слота, анализ метрик, abort) |
| Почему blue-green, а не canary? | Простая модель отката, и blue-green можно проверить на одном узле. Canary (новая версия получает долю трафика) потребовал бы TraefikService/weighted routing и усложнил бы оценку метрик на малом трафике |
| Что если два человека запустят релиз? | Релиз берёт блокировку — Lease `mts-api-change-lock` в кластере. Второй запуск получает отказ с именем держателя блокировки (код 10). Сценарий `concurrency` |
| Что если релиз прервали? | Фаза релиза хранится в ConfigMap. `make recover` или следующий релиз возвращает трафик на последний подтверждённый релиз и снимает зависшие Helm-ревизии. Сценарий `interrupted` |
| Почему Alpine? | Сравнение Trivy: Debian slim — 166 находок (44 HIGH без исправлений), Alpine 3.24 — 1 MEDIUM. Образ — 29 МБ сжатых слоёв |
| Почему нет kube-prometheus-stack? | Он тяжелее, чем позволяет цель 4 vCPU / 8 ГБ, и его сложнее объяснить. Собственный чарт — ≈ 600 строк шаблонов и values (D12) |
| Сколько ресурсов? | В покое весь стенд занимает ≈ 1,6 ГиБ RAM, узел k3d — ~0,2 vCPU (замер `docker stats`) |
