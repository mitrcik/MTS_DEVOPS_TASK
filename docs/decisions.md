# Архитектурные решения (ADR-лог)

Формат: решение → почему → альтернативы → последствия. Источники требований:
Word «Конкурс кейсов DevOps 2.1» (кейс 1), расшифровка ВКС (таймкоды `[мм:сс]`).
Решения этого проекта — инженерный выбор команды, а не требования МТС.

## D1. Основной профиль: Ubuntu 24.04 → Docker → k3d (k3s) → Helm

- **Почему.** Жюри воспроизводит решение на Ubuntu [04:40, 08:37] и само клонирует репозиторий
  [06:27, 30:18]. Однонодовый k3d прямо разрешён, если команда понимает его устройство [24:27].
  k3d поднимает настоящий k3s (API, kubelet, containerd, Traefik, NetworkPolicy-контроллер) в
  контейнере за ~15 с и не требует гипервизора.
- **Замена буквального пункта Word.** Пункт «Terraform/Ansible — развернуть ВМ/инстанс» в основном
  профиле заменён контейнерным узлом k3d. **Контейнерный узел k3d — не виртуальная машина**, Terraform
  в проекте не используется. Ansible автоматизирует весь жизненный цикл стенда.
- **Альтернативы.** minikube (тяжелее, нужен драйвер); kind (нет встроенных Traefik/NP-контроллера/
  шифрования Secret); ВМ через libvirt/OpenStack (в среде разработки нет `/dev/kvm` и OpenStack —
  проверить нельзя, поэтому профиль ВМ описан как развитие, см. D13).
- **Последствия.** Один узел: нет отказоустойчивости инфраструктуры; это стенд практик доставки,
  а не production-кластер. Путь к HA — в `docs/architecture.md`.

## D2. Ansible как оркестратор, Helm для приложений

- **Почему.** Ведущий допустил «плейбук, который вызывает helm upgrade» [24:20] и любые
  обоснованные инструменты [02:26, 36:48]. Ansible даёт идемпотентные шаги с понятным выводом,
  проверку sha256 загрузок (`get_url checksum`), шаблоны (`k3d-cluster.yaml.j2`) и тот же плейбук
  можно направить на удалённый Ubuntu-хост через inventory.
- **Альтернативы.** Голый bash (хуже идемпотентность и читаемость); Terraform (для k3d-кластера
  на локальном Docker избыточен, провайдеры k3d — сторонние).
- **Последствия.** Нужен Python venv (`python3-venv` из Ubuntu); версии ansible-core и зависимостей
  закреплены по хешам (`infra/tooling/requirements.lock`).

## D3. Blue-green (а не canary), один владелец маршрутизации

- **Почему.** Кейс допускает blue-green или canary. Blue-green даёт простую и проверяемую модель
  отката: «вернуть селектор на прежний слот», прежний слот всё время работает.
- **Как.** Два Helm-релиза слотов `mts-api-blue`/`mts-api-green` (charts/app) владеют только своими
  Deployment/Service/NetworkPolicy. Стабильный Service `mts-api-active` и Ingress принадлежат
  единственному релизу `mts-api-traffic` (charts/traffic); переключение = смена `activeSlot`.
  Схема чарта traffic **требует** явный `activeSlot` — повторный `helm upgrade` не может незаметно
  вернуть слот «по умолчанию» и отменить выполненный откат.
- **Источник истины.** Фактическая маршрутизация — селектор живого Service. ConfigMap
  `mts-api-release-state` хранит последний подтверждённый здоровый релиз, фазу операции и историю.
- **Почему не Argo Rollouts/Flagger.** Дополнительный контроллер с CRD, больше движущихся частей;
  собственный контроллер (`scripts/pylib/release.py` ≈ 760 строк; вместе с gate, блокировкой, состоянием и
  отчётами ≈ 1 300 строк кода) команда может объяснить построчно.

## D4. Ingress — встроенный Traefik k3s, все порты только на loopback

- Traefik уже входит в k3s, умеет Kubernetes Ingress и маршрутизирует на endpoints Service,
  поэтому смена селектора Service — атомарное для пользователя переключение.
- k3d без балансировщика (`disableLoadbalancer`): один узел, порт `127.0.0.1:8080 → :80` узла.
- UI наблюдаемости — по Host-заголовку `*.localhost` (браузеры и curl резолвят `*.localhost`
  в 127.0.0.1 без правки `/etc/hosts`). Локальный HTTP без TLS — ограничение демо-профиля.

## D5. Registry: k3d-registry локально, GHCR для удалённого конвейера

- Жюри проверяет без GitHub-токена: `make up` поднимает registry `127.0.0.1:5001`.
  Внутри узла `localhost:5001` — это сам узел, поэтому в `registries.yaml` k3s настроено зеркало
  `localhost:5001 → http://<registry-container>:5000` в общей docker-сети. Проверено:
  push с хоста → pull узлом по digest → запуск pod.
- GitHub Actions публикует в GHCR (`GITHUB_TOKEN`, `packages: write` только в job публикации).

## D6. Развёртывание только по digest, тег связан с Git SHA

- Тег `<git-sha12>-<version>[-fault-<mode>]`; в Kubernetes уходит `repo@sha256:…`
  (`values.schema.json` чарта отвергает что-либо кроме digest).
- Образ сканируется до публикации; перед push проверяется, что тег всё ещё указывает на тот же
  локальный image ID; release controller принимает только provenance с `trivy.result=passed`
  и совпадающим digest.

## D7. Политика Trivy

- Блокируют: HIGH/CRITICAL **с доступным исправлением** и любые найденные секреты.
  HIGH/CRITICAL без исправления считаются и выводятся, но не блокируют (их нельзя устранить
  обновлением; это документированный риск).
- Исключения — только адресно в `.trivyignore.yaml` с `statement` и `expired_at` (≤ 90 дней),
  проверяется в CI.
- Ошибка сканера/базы — провал стадии: Trivy запускается с `--exit-code 0` только для отделения
  «находок» от «сбоя», решение принимает политика по JSON-отчёту, а отсутствие отчёта или метаданных
  базы — провал.
- **База образа.** Сравнение на одном и том же коде и lock-файле (Trivy 0.75.0, БД от 2026-10-15):
  `python:3.13-slim-trixie` — 166 находок, из них 44 HIGH без доступного исправления, 52 МБ;
  `python:3.13-alpine3.24` — 1 MEDIUM, 29 МБ (сжатые слои; ≈ 122 МБ распакованный). Выбрана Alpine: меньше пакетов — меньше поверхность
  атаки и шума в отчётах. Колёса musllinux для pydantic-core есть в lock-файле (хеши всех колёс).
- **Компромисс.** База задана минорными версиями и собирается с `--pull`: так она получает
  исправления безопасности, а фактический digest базы записывается в provenance. Жёсткое
  закрепление по digest сделало бы сборку побитово стабильнее, но через несколько недель такая
  база с высокой вероятностью перестала бы проходить политику Trivy у жюри.

## D8. Секреты: SOPS + age; в кластере — хеши токенов

- SOPS + age — единственный механизм шифрования файлов секретов (Vault/Sealed Secrets требуют
  дополнительного серверного компонента).
- Закрытый age-ключ хранится **вне каталога проекта**: `~/.config/mts-devops/<cluster>/age.key`
  (0600), отдельно от зашифрованного источника `.local/secrets/app-secrets.sops.yaml` (0600).
- Plaintext не пишется на диск: генерация → `sops encrypt` из stdin → файл; применение —
  `sops decrypt` в память → `kubectl apply --server-side -f -` (без аннотации last-applied).
- В Secret `api-auth` лежат только SHA-256 токенов; сам токен есть только в SOPS-файле.
- k3s запускается с `--secrets-encryption` (AES-CBC): Secret в базе kine зашифрованы
  (проверяется `make verify-security`). Base64 в Kubernetes API — не шифрование, это учтено.

## D9. Ротация с перекрытием

- Фаза overlap (старый и новый токены действуют) → проверка каждого pod **обоих** слотов →
  отзыв старого → проверка каждого pod → проверка через ingress.
- Оба слота читают один Secret как файл (kubelet обновляет volume), приложение перечитывает файл
  при изменении inode/mtime — откат на «старый» слот не возвращает отозванный токен.
- Ускорение синхронизации: аннотация pod заставляет kubelet сразу пересинхронизировать volume.

## D10. Gate после переключения: HTTP-нагрузка + метрики, fail closed

- HTTP-поток через реальный ingress (≈8 rps, смесь методов, токен из SOPS) с ранней остановкой.
- Метрики Prometheus по слоту кандидата: число запросов ≥ минимума, доля 5xx, p95 по histogram,
  свежесть scrape каждого pod, `app_build_info` с release id кандидата.
- Нет Prometheus / пустой вектор / NaN / мало трафика / устаревшие серии → провал, а не успех.
- Пороги и длительность окна — в `.env` (демо: окно 30 с, ошибки ≤ 2 %, p95 ≤ 0,5 с).

## D11. Блокировка стенда — Lease в кластере

- `coordination.k8s.io/v1 Lease mts-api-change-lock`: атомарный create, продление и перехват
  просроченной блокировки через `replace` с `resourceVersion`. Работает между машинами
  (локальный запуск и удалённый CD конкурируют за один объект). Релизы, ротация и демо-алерт
  используют одну блокировку.

## D12. Наблюдаемость — собственный минимальный чарт вместо kube-prometheus-stack

- Требование кейса — Prometheus + Grafana, ≥1 дашборд, ≥1 алерт. kube-prometheus-stack тянет
  оператор, CRD, node-exporter, kube-state-metrics и сотни правил — тяжелее цели 4 vCPU/8 ГБ и хуже
  объясняется на защите. Свой чарт (`observability/`) — ≈ 600 строк шаблонов и values (плюс конфигурации и дашборд в
  `observability/files/`), всё в репозитории [02:58, 33:44].
- Prometheus 3.13.4, Alertmanager 0.34.1, Grafana 13.2.3, blackbox exporter 0.28.0.
- cAdvisor снимается напрямую с kubelet с правом `nodes/metrics` (а не `nodes/proxy`) и проверкой
  TLS по CA кластера.
- Главный алерт — синтетическая проба бизнес-метода через ingress (`probe_success`): он работает,
  даже когда метрик приложения нет совсем.

## D13. Что сознательно не делалось

- Автоматическое создание ВМ (Terraform/libvirt или OpenStack, cloud-init): нет KVM/OpenStack для
  проверки — фиктивных модулей нет. Подготовка уже созданной ВМ автоматизирована (D16).
- Canary, service mesh, Loki, трассировки, Chaos Mesh, Telegram, runtime-LLM — вне кейса 1.
- Compose вместо Kubernetes [12:36] не выбран: доставка в кластер и переключение релизов — предмет кейса.

## D16. Запуск на ВМ пользователя: Ubuntu 22.04–26.04, x86_64 и arm64

- **Решение.** `make prereqs` (`scripts/install-prereqs.sh`) готовит чистую Ubuntu: `docker.io` и
  `docker-buildx` из архивов Ubuntu (одна и та же версия 29.1.3 в 22.04, 24.04 и 26.04 — без сторонних
  репозиториев и ключей), Python ≥ 3.12 с venv (на 22.04 — `python3.12` из PPA deadsnakes, ключ
  сверяется по отпечатку), лимиты inotify, группа `docker`. Уже установленный Docker CE не трогается.
- **arm64.** Все CLI закреплены для amd64 и arm64 с sha256; все, кроме age (проект не публикует файл checksum —
  хеш зафиксирован при закреплении версии), сверены с официальными файлами checksum
  (`infra/tools/tools.yml`, проверка `cihelper check-tool-pins` в `compat.yml`); образы стенда
  мультиархитектурные, lock-файлы Python содержат хеши колёс aarch64 (проверено `pip download`).
- **Проверка.** Workflow `compat.yml`: чистые ВМ GitHub (Ubuntu 22.04 x86_64, 24.04 aarch64) и
  окружение Ubuntu 22.04/24.04/26.04 в контейнере — `make prereqs` → `make up` → 15 сценариев.
- **Почему не Docker CE из download.docker.com.** Пакеты Ubuntu не требуют стороннего ключа и
  репозитория и одинаково доступны во всех трёх LTS; версии ≥ 24 достаточно (BuildKit secrets).
- **Безопасность.** Порты стенда остаются на loopback ВМ; UI с компьютера пользователя — через
  SSH-туннель, а не открытием портов (`docs/vm-guide.md` §5).

## D14. Правило выбора версий

Зафиксировано 2026-10-15: последний стабильный выпуск, опубликованный не позже 2026-10-01
(без RC и релизов «нулевого дня»). Для Python-зависимостей правило воспроизводимо: `make lock`
(`uv pip compile --exclude-newer 2026-10-01`). Версии из шаблона Word (k3s 1.28 и т.п.) не
обязательны [29:47]. Таблица — в README («Инструменты»).

## D15. Особенности среды разработки (не влияют на путь жюри)

Проект разрабатывался и проверялся в облачной Ubuntu 24.04 с ограничениями сети и ядра. Для неё
использовались только штатные параметры, оставшиеся пустыми в `.env.example`:

| ограничение среды | что сделано | влияет ли на жюри |
|---|---|---|
| хост на cgroup v1 (Ubuntu 24.04 по умолчанию v2) | роль cluster автоматически добавляет `--kubelet-arg=fail-cgroupv1=false`, только если `docker info` сообщает cgroup v1 | нет, на cgroup v2 флаг не добавляется |
| TLS-перехват исходящего трафика | `EXTRA_CA_BUNDLE` (BuildKit secret при сборке, монтирование в узел k3s) | нет, по умолчанию пусто |
| лимит Docker Hub 429 | `DOCKERHUB_MIRROR=https://mirror.gcr.io` + `registry-mirrors` демона Docker | нет, по умолчанию пусто |
| нет `CAP_SYS_RESOURCE` у root | `K3D_EXTRA_ARGS` монтирует конфиг containerd с `restrict_oom_score_adj` | нет |
| закрыты get.helm.sh и блобы ghcr.io | helm 4.3.0 взят из образа `alpine/helm:4.3.0`; служебный образ k3d-tools — `K3D_IMAGE_TOOLS=rancher/k3d-tools:5.3.0` | нет; путь get.helm.sh/ghcr проверяется в GitHub Actions |
