# Архитектурные решения (ADR-лог)

ADR (Architecture Decision Record) — короткая запись инженерного решения. Для каждого решения
указано: что выбрано, почему, какие были альтернативы и к чему это приводит.

Источники требований: документ кейса «Конкурс кейсов DevOps 2.1» (кейс 1) и ответы организаторов
на консультации. Решения ниже — инженерный выбор команды, а не требования МТС.

## D1. Основной профиль: Ubuntu 24.04 → Docker → k3d (k3s) → Helm

- **Почему.** На консультации организаторы сообщили: жюри само клонирует репозиторий и запускает
  решение на Ubuntu. Организаторы разрешили k3d с одной нодой, если команда понимает, как он устроен.
  k3d запускает настоящий k3s (API, kubelet, containerd, Traefik, контроллер NetworkPolicy) внутри
  Docker-контейнера. Кластер поднимается примерно за 15 с, гипервизор не нужен.
- **Отличие от буквального текста кейса.** Пункт кейса «Terraform/Ansible — развернуть ВМ/инстанс»
  в основном профиле заменён контейнерным узлом k3d. **Контейнерный узел k3d — не виртуальная
  машина.** Terraform в проекте не используется. Ansible автоматизирует весь жизненный цикл стенда.
- **Альтернативы.**
  - minikube — тяжелее, нужен драйвер.
  - kind — нет встроенных Traefik, контроллера NetworkPolicy и шифрования Secret.
  - ВМ через libvirt/OpenStack — в среде разработки нет `/dev/kvm` и OpenStack, поэтому проверить
    такой профиль нельзя. Профиль ВМ описан как направление развития (см. D13).
- **Последствия.** Узел один, поэтому отказоустойчивости инфраструктуры нет. Это стенд для показа
  практик доставки, а не production-кластер. Путь к HA (высокой доступности) описан в
  [`architecture.md`](architecture.md), раздел 7.

## D2. Ansible как оркестратор, Helm для приложений

- **Почему.** На консультации организаторы разрешили «плейбук, который вызывает helm upgrade» и любые
  обоснованные инструменты. Что даёт Ansible:
  - идемпотентные шаги с понятным выводом (повторный запуск не ломает уже готовое);
  - проверку sha256 загрузок (`get_url checksum`);
  - шаблоны (`k3d-cluster.yaml.j2`);
  - запуск того же плейбука на удалённом Ubuntu-хосте через inventory.
- **Альтернативы.** Голый bash — хуже идемпотентность и читаемость. Terraform — избыточен для
  k3d-кластера на локальном Docker, а провайдеры k3d для него сторонние.
- **Последствия.** Нужен Python venv (`python3-venv` из Ubuntu). Версии ansible-core и зависимостей
  закреплены по хешам (`infra/tooling/requirements.lock`).

## D3. Blue-green (а не canary), один владелец маршрутизации

- **Почему.** Кейс допускает blue-green или canary. Blue-green — это два слота приложения, трафик
  переключается между ними. Откат в такой модели простой и проверяемый: селектор Service
  возвращается на прежний слот, а прежний слот всё это время работает.
- **Как.**
  - Слоты — два Helm-релиза `mts-api-blue` и `mts-api-green` (`charts/app`). Каждый владеет только
    своими Deployment, Service и NetworkPolicy.
  - Стабильный Service `mts-api-active` и Ingress принадлежат одному релизу `mts-api-traffic`
    (`charts/traffic`). Переключение — это смена значения `activeSlot`.
  - Схема чарта traffic **требует** явный `activeSlot`. Поэтому повторный `helm upgrade` не может
    незаметно вернуть слот «по умолчанию» и отменить выполненный откат.
- **Источник истины.** Куда на самом деле идёт трафик, показывает селектор живого Service. ConfigMap
  `mts-api-release-state` хранит последний подтверждённый здоровый релиз, фазу операции и историю.
- **Почему не Argo Rollouts/Flagger.** Это дополнительный контроллер с CRD, то есть больше
  компонентов. Собственный контроллер команда может объяснить построчно: `scripts/pylib/release.py` —
  ≈ 760 строк, вместе с gate, блокировкой, состоянием и отчётами — ≈ 1 300 строк кода.

## D4. Ingress — встроенный Traefik k3s, все порты только на loopback

- Traefik уже входит в k3s и поддерживает Kubernetes Ingress. Он отправляет запросы на endpoints
  Service. Поэтому для пользователя смена селектора Service — атомарное переключение.
- k3d работает без балансировщика (`disableLoadbalancer`): узел один, порт `127.0.0.1:8080`
  проброшен на порт `:80` узла.
- Интерфейсы наблюдаемости открываются по Host-заголовку `*.localhost`. Браузеры и curl сами
  резолвят `*.localhost` в 127.0.0.1, правка `/etc/hosts` не нужна.
- Локальный HTTP без TLS — ограничение демо-профиля.

## D5. Registry: k3d-registry локально, GHCR для удалённого конвейера

- Жюри проверяет решение без GitHub-токена. Поэтому `make up` поднимает локальный registry
  `127.0.0.1:5001`.
- Внутри узла адрес `localhost:5001` указывает на сам узел. Поэтому в `registries.yaml` k3s
  настроено зеркало `localhost:5001 → http://<registry-container>:5000` в общей docker-сети.
  Проверено: push с хоста → pull узлом по digest → запуск pod.
- GitHub Actions публикует образ в GHCR (`GITHUB_TOKEN`). Право `packages: write` есть только у job
  публикации.

## D6. Развёртывание только по digest, тег связан с Git SHA

- Digest — неизменяемый хеш содержимого образа. Тег образа: `<git-sha12>-<version>[-fault-<mode>]`.
  В Kubernetes уходит ссылка по digest `repo@sha256:…`; `values.schema.json` чарта отвергает всё,
  кроме digest.
- Образ сканируется до публикации. Перед push проверяется, что тег всё ещё указывает на тот же
  локальный image ID.
- Release controller принимает только provenance (файл о происхождении образа) с
  `trivy.result=passed` и совпадающим digest.

## D7. Политика Trivy

- Публикацию образа блокируют уязвимости HIGH/CRITICAL **с доступным исправлением** и любые
  найденные секреты.
- HIGH/CRITICAL без исправления считаются и выводятся, но не блокируют. Их нельзя устранить
  обновлением; это документированный риск.
- Исключения добавляются только адресно в `.trivyignore.yaml`, с `statement` и `expired_at`
  (≤ 90 дней). Это проверяется в CI.
- Ошибка сканера или базы уязвимостей — провал стадии. Trivy запускается с `--exit-code 0` только
  для того, чтобы отделить «находки» от «сбоя». Решение принимает политика по JSON-отчёту. Если нет
  отчёта или метаданных базы — стадия проваливается.
- **Базовый образ.** Сравнение на одном и том же коде и lock-файле (Trivy 0.75.0, БД от 2026-10-15):
  - `python:3.13-slim-trixie` — 166 находок, из них 44 HIGH без доступного исправления, 52 МБ;
  - `python:3.13-alpine3.24` — 1 MEDIUM, 29 МБ (сжатые слои; ≈ 122 МБ в распакованном виде).

  Выбрана Alpine: меньше пакетов — меньше поверхность атаки и меньше шума в отчётах. Колёса
  (wheel-пакеты Python) musllinux для pydantic-core есть в lock-файле, с хешами всех колёс.
- **Компромисс.** База задана минорными версиями и собирается с `--pull`. Так она получает
  исправления безопасности, а фактический digest базы записывается в provenance. Жёсткое закрепление
  по digest сделало бы сборку побитово стабильнее. Но через несколько недель такая база с высокой
  вероятностью перестала бы проходить политику Trivy у жюри.

## D8. Секреты: SOPS + age; в кластере — хеши токенов

- SOPS + age — единственный механизм шифрования файлов секретов. Vault и Sealed Secrets требуют
  дополнительного серверного компонента.
- Закрытый age-ключ хранится **вне каталога проекта**: `~/.config/mts-devops/<cluster>/age.key`
  (0600). Зашифрованный источник лежит отдельно: `.local/secrets/app-secrets.sops.yaml` (0600).
- Открытый текст секретов не пишется на диск:
  - создание: генерация → `sops encrypt` из stdin → файл;
  - применение: `sops decrypt` в память → `kubectl apply --server-side -f -` (без аннотации
    last-applied).
- В Secret `api-auth` лежат только SHA-256 токенов. Сам токен есть только в SOPS-файле.
- k3s запускается с `--secrets-encryption` (AES-CBC), поэтому Secret в базе kine зашифрованы. Это
  проверяет `make verify-security`. Base64 в Kubernetes API — не шифрование, это учтено.

## D9. Ротация с перекрытием

Ротация с перекрытием: какое-то время старый и новый токены действуют одновременно.

- Порядок шагов:
  1. Фаза overlap: действуют старый и новый токены.
  2. Проверка каждого pod **обоих** слотов.
  3. Отзыв старого токена.
  4. Проверка каждого pod.
  5. Проверка через ingress.
- Оба слота читают один Secret как файл (kubelet обновляет volume). Приложение перечитывает файл,
  когда меняются inode или mtime. Поэтому откат на «старый» слот не возвращает отозванный токен.
- Синхронизацию ускоряет аннотация pod: она заставляет kubelet сразу пересинхронизировать volume.

## D10. Gate после переключения: HTTP-нагрузка + метрики, fail closed

Gate — автоматическая проверка, которая решает, оставить новый релиз или откатить его. Fail closed:
если данных для решения нет, проверка считается проваленной.

- HTTP-поток идёт через реальный ingress: ≈ 8 rps, смесь методов, токен из SOPS. При явном провале
  окно наблюдения останавливается досрочно.
- Метрики Prometheus по слоту-кандидату:
  - число запросов — не меньше минимума;
  - доля ответов 5xx;
  - p95 по histogram;
  - свежесть scrape каждого pod;
  - `app_build_info` с release id кандидата.
- Нет Prometheus, пустой вектор, NaN, мало трафика или устаревшие серии — это провал, а не успех.
- Пороги и длительность окна задаются в `.env`. Для демо: окно 30 с, ошибки ≤ 2 %, p95 ≤ 0,5 с.

## D11. Блокировка стенда — Lease в кластере

Блокировка не даёт двум операциям менять стенд одновременно.

- Объект блокировки — `coordination.k8s.io/v1 Lease mts-api-change-lock`. Захват — атомарный
  create. Блокировку можно продлевать. Просроченную блокировку перехватывают через `replace` с
  `resourceVersion`.
- Блокировка работает между машинами: локальный запуск и удалённый CD конкурируют за один объект.
- Релизы, ротация и демо-алерт используют одну и ту же блокировку.

## D12. Наблюдаемость — собственный минимальный чарт вместо kube-prometheus-stack

- Кейс требует Prometheus + Grafana, не меньше одного дашборда и одного алерта.
- kube-prometheus-stack тянет оператор, CRD, node-exporter, kube-state-metrics и сотни правил. Это
  тяжелее цели 4 vCPU/8 ГБ и сложнее объяснить на защите.
- Свой чарт (`observability/`) — ≈ 600 строк шаблонов и values, плюс конфигурации и дашборд в
  `observability/files/`. Всё лежит в репозитории, без приватных компонентов, как просили
  организаторы на консультации.
- Версии: Prometheus 3.13.4, Alertmanager 0.34.1, Grafana 13.2.3, blackbox exporter 0.28.0.
- Метрики cAdvisor снимаются напрямую с kubelet. Для этого используется право `nodes/metrics`
  (а не `nodes/proxy`), TLS проверяется по CA кластера.
- Главный алерт — синтетическая проба бизнес-метода через ingress (`probe_success`). Он работает,
  даже когда метрик приложения нет совсем.

## D13. Что сознательно не делалось

- **Автоматическое создание ВМ** (Terraform/libvirt или OpenStack, cloud-init). Нет KVM/OpenStack
  для проверки, поэтому фиктивных модулей в проекте нет. Подготовка уже созданной ВМ автоматизирована
  (D16).
- **Canary, service mesh, Loki, трассировки, Chaos Mesh, Telegram, runtime-LLM** — вне кейса 1.
- **Compose вместо Kubernetes.** Организаторы на консультации допускали Compose для простых
  контейнерных решений. Мы его не выбрали: доставка в кластер и переключение релизов — предмет кейса.

## D14. Правило выбора версий

Правило зафиксировано 2026-10-15: берётся последний стабильный выпуск, опубликованный не позже
2026-10-01. RC и релизы «нулевого дня» не используются. Для Python-зависимостей правило
воспроизводимо: `make lock` (`uv pip compile --exclude-newer 2026-10-01`). Организаторы на
консультации подтвердили, что версии из шаблона кейса (k3s 1.28 и т.п.) не обязательны. Таблица
версий — в [README](../README.md), раздел «Использованные инструменты».

## D15. Особенности среды разработки (не влияют на путь жюри)

Проект разрабатывался и проверялся в облачной Ubuntu 24.04 с ограничениями сети и ядра. Для неё
использовались только штатные параметры. В `.env.example` они оставлены пустыми.

| Ограничение среды | Что сделано | Влияет ли на жюри |
|---|---|---|
| хост на cgroup v1 (Ubuntu 24.04 по умолчанию использует v2) | роль cluster добавляет `--kubelet-arg=fail-cgroupv1=false` автоматически и только если `docker info` сообщает cgroup v1 | нет, на cgroup v2 флаг не добавляется |
| TLS-перехват исходящего трафика | `EXTRA_CA_BUNDLE` (BuildKit secret при сборке, монтирование в узел k3s) | нет, по умолчанию пусто |
| лимит Docker Hub 429 | `DOCKERHUB_MIRROR=https://mirror.gcr.io` + `registry-mirrors` демона Docker | нет, по умолчанию пусто |
| нет `CAP_SYS_RESOURCE` у root | `K3D_EXTRA_ARGS` монтирует конфиг containerd с `restrict_oom_score_adj` | нет |
| закрыты get.helm.sh и блобы ghcr.io | helm 4.3.0 взят из образа `alpine/helm:4.3.0`; служебный образ k3d-tools — `K3D_IMAGE_TOOLS=rancher/k3d-tools:5.3.0` | нет; путь get.helm.sh/ghcr проверяется в GitHub Actions |

## D16. Запуск на ВМ пользователя: Ubuntu 22.04–26.04, x86_64 и arm64

- **Решение.** `make prereqs` (`scripts/install-prereqs.sh`) готовит чистую Ubuntu:
  - `docker.io` и `docker-buildx` из архивов Ubuntu: одна и та же версия 29.1.3 в 22.04, 24.04 и
    26.04, без сторонних репозиториев и ключей;
  - Python ≥ 3.12 с venv (на 22.04 — `python3.12` из PPA deadsnakes, ключ сверяется по отпечатку);
  - лимиты inotify;
  - группа `docker`.

  Уже установленный Docker CE не трогается.
- **arm64.** Все CLI закреплены для amd64 и arm64 с sha256 (`infra/tools/tools.yml`). Хеши всех CLI,
  кроме age, сверены с официальными файлами checksum; это проверяет `cihelper check-tool-pins` в
  `compat.yml`. Проект age не публикует файл checksum, поэтому его хеш зафиксирован при закреплении
  версии. Образы стенда мультиархитектурные. Lock-файлы Python содержат хеши колёс aarch64
  (проверено `pip download`).
- **Проверка.** Workflow `compat.yml` выполняет `make prereqs` → `make up` → 15 сценариев:
  - на чистых ВМ GitHub: Ubuntu 22.04 x86_64 и 24.04 aarch64;
  - в окружении Ubuntu 22.04/24.04/26.04 в контейнере.
- **Почему не Docker CE из download.docker.com.** Пакеты Ubuntu не требуют стороннего ключа и
  репозитория и одинаково доступны во всех трёх LTS. Версии ≥ 24 достаточно (нужны BuildKit secrets).
- **Безопасность.** Порты стенда остаются на loopback ВМ. Веб-интерфейсы с компьютера пользователя
  открываются через SSH-туннель, а не через открытые порты ([`vm-guide.md`](vm-guide.md), раздел 5).
